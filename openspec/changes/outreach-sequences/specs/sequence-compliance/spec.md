# Sequence Compliance Specification

## Purpose

Define CAN-SPAM obligations for automated commercial email to US recipients: a valid physical postal address in every message, a working opt-out honoured within 10 business days, and a send-suppression list that the roster and the scheduler both consult. This is a legal requirement the mockup does not yet design.

## Open owner decision (blocking for the opt-out mechanism, not for the rest)

The owner MUST choose one of the two mechanisms below before implementation of that part. Requirements marked **[Both]** apply regardless. Requirements marked **[Option A]** or **[Option B]** apply only to the chosen option.

| | Option A: reply-based | Option B: tracked link |
|---|---|---|
| Opt-out text | Plain-text line: reply with "unsubscribe" or "no more emails" | Link in the footer |
| Address | Miami office postal address in the signature | Same |
| Needs new infrastructure | Little: a BD action to record an opt-out | A public route, per-recipient token, suppression list |
| Honouring | A reply already stops the sequence; the BD records the opt-out | Automatic on click |
| Risk | Depends on the BD noticing and recording opt-outs | New public, unauthenticated endpoint to secure |

The owner must also supply the exact postal address string (the Miami office address is not recorded in the codebase) and confirm with counsel that the advertisement-disclosure and "accurate subject line" obligations are met by the generated copy. This spec does not give legal advice.

## Requirements

### Requirement: [Both] Postal address and opt-out line in every message

Every email a Sequence sends (step 1 and step 2) MUST contain the sender's valid physical postal address and a clear opt-out instruction. These MUST be appended deterministically by the system from configuration, NOT generated by the model and NOT dependent on the model following a prompt rule. The existing generator signs off with the sender's name only; the compliance footer is added after the generated body. The footer MUST be visible, unmodified, in the review dialog, and MUST be part of what the BD approves.

#### Scenario: Footer appended to the draft

- GIVEN a generated draft ending with the sender's name
- WHEN the draft is stored for review
- THEN the body ends with the postal address and the opt-out instruction

#### Scenario: Footer shown in review

- GIVEN the BD opens "Revisar borrador"
- WHEN the dialog renders
- THEN the footer text is visible as part of the body

#### Scenario: Reminder carries the footer too

- GIVEN a reminder draft
- WHEN it is stored
- THEN it has the same footer

#### Scenario: Model output cannot omit it

- GIVEN a generator response that contains no address or opt-out
- WHEN the draft is stored
- THEN the footer is still present

### Requirement: [Both] Send is refused without the footer

The runner MUST refuse to send any message whose final body does not contain the configured postal address and opt-out instruction, even if the BD edited them away. The member MUST be held with a visible reason. This MUST be a pure, unit-testable check on the final body.

#### Scenario: BD deletes the footer while editing

- GIVEN an approved draft whose body no longer contains the configured address
- WHEN the runner considers it
- THEN it is not sent and the card shows why

#### Scenario: Edit save warns

- GIVEN the BD saves an edit that removes the footer
- WHEN the save completes
- THEN the BD is told the message cannot be sent until the footer is restored

### Requirement: [Both] Truthful headers and subject

The From identity MUST be the real sending account (see `sequence-scheduling`). The subject MUST NOT be deceptive about the content of the message and MUST NOT use a "Re:" or "Fwd:" prefix on a step 1 email (the existing generator already forbids "Re:").

#### Scenario: Step 1 subject with Re:

- GIVEN an edited step 1 subject beginning with "Re:"
- WHEN the BD tries to approve
- THEN the approval is rejected with an explanation

### Requirement: [Both] Send-suppression list

The system MUST keep a list of addresses (and optionally domains) that must never receive Sequence email. The list MUST be consulted (a) by the roster picker and add action and (b) by the runner immediately before every send. The suppression check MUST be a pure function over (address, rules) and unit-testable.

Design caution on storage: the existing `email_never_log` table is the owner's suggested home, but it carries different semantics. It is per BD and means "never log this correspondent's mail"; the classifier discards entire messages involving such addresses, which would also hide a reply from the correspondent and break reply detection. CAN-SPAM opt-out also binds the company, not one BD. The design MUST either extend that table with a distinct purpose and a company-wide scope, or use a separate table, and MUST state how reply detection still sees messages from suppressed addresses.

#### Scenario: Suppressed address never sent to

- GIVEN a suppressed address on an approved member
- WHEN the runner executes
- THEN nothing is sent to that address

#### Scenario: Suppression is case-insensitive

- GIVEN a suppression entry `jane@acme.com`
- WHEN a member's address is `Jane@Acme.com`
- THEN it is treated as suppressed

#### Scenario: Domain-level suppression

- GIVEN a domain rule `acme.com`
- WHEN any member address at `acme.com` is checked
- THEN it is suppressed

#### Scenario: Suppression is company-wide

- GIVEN BD A recorded an opt-out for an address
- WHEN BD B tries to add the same Contact to their Sequence
- THEN the add is rejected

### Requirement: [Both] Opt-out honoured within 10 business days, in practice immediately

An opt-out MUST stop every active Sequence membership for that address as soon as it is recorded, and MUST prevent any future Sequence send. The system MUST NOT depend on the 10-business-day allowance for its own behaviour; it is a legal ceiling, not a design target. The opt-out mechanism MUST remain functional for at least 30 days after each message is sent, MUST NOT require a fee, login, or additional personal information beyond the address, and MUST NOT be used to send further commercial email.

#### Scenario: Opt-out stops all memberships

- GIVEN a Contact who is an active member in two Sequences
- WHEN their opt-out is recorded
- THEN both memberships become `discarded` with reason "opt-out" and no further step is sent

#### Scenario: Opt-out is not reversible by re-admit

- GIVEN a discarded opt-out member
- WHEN the BD tries "Reincorporar"
- THEN it is rejected

### Requirement: [Option A] Reply-based opt-out is recorded by the BD

If Option A is chosen, the member card and the Contact record MUST offer an explicit "No contactar" action that records the suppression entry. A reply already moves the member to `replied` and stops the sequence; the action covers the longer-term suppression. The system SHOULD flag inbound replies containing common opt-out phrases ("unsubscribe", "remove me", "stop emailing", "no more emails") so the BD sees a prompt to record the opt-out. Phrase detection is advisory and MUST NOT be the only path to suppression.

#### Scenario: BD records opt-out from a reply

- GIVEN a member who replied "please remove me from your list"
- WHEN the BD uses "No contactar"
- THEN the address is suppressed and all their memberships are discarded

#### Scenario: Phrase detection is advisory

- GIVEN an inbound reply containing "unsubscribe"
- WHEN the card renders
- THEN a prompt to record the opt-out is shown
- AND the address is not suppressed until the BD acts

#### Scenario: Opt-out text in footer

- GIVEN Option A
- WHEN a footer is built
- THEN it instructs the recipient to reply to opt out

### Requirement: [Option B] Tracked unsubscribe link

If Option B is chosen, every message MUST include a per-recipient unsubscribe link carrying an unguessable, non-enumerable token. The public route that serves it MUST accept the opt-out without login, MUST be idempotent, MUST write the suppression entry, and MUST respond with a plain confirmation that reveals nothing about other recipients. The route MUST be excluded from the session gate but MUST NOT be able to perform any other action. Tokens MUST be bound to one recipient and one Sequence member and MUST remain valid for at least 30 days after the send.

#### Scenario: Valid token

- GIVEN a valid token for a member
- WHEN the link is opened
- THEN the address is suppressed and the memberships are discarded

#### Scenario: Repeat click

- GIVEN a token already used
- WHEN the link is opened again
- THEN the same confirmation is shown and nothing changes

#### Scenario: Invalid token

- GIVEN a malformed or unknown token
- WHEN the link is opened
- THEN a generic response is returned and no suppression is written

### Requirement: [Both] Postal address is configuration

The postal address and opt-out text MUST come from a single configuration source, not from copy scattered in prompts or components, so that the later migration to a sending subdomain or a different office address is a configuration change.

#### Scenario: Address changes in one place

- GIVEN the configured address is updated
- WHEN a new draft is generated
- THEN the new address appears and no other file needed editing
